# Proposals

ข้อเสนอทางเทคนิคที่ยังไม่ตัดสินใจขั้นสุดท้าย เก็บเหตุผลและทางเลือกไว้ที่นี่ เพื่อให้กลับมาอ่านแล้วรู้ว่าเคยชั่งน้ำหนักอะไรไปแล้วบ้าง

## 1. การนำเข้าข้อมูลครั้งแรก

**ปัญหา:** เกมไม่มี API และ MR มี monster หลายร้อยตัว การกรอกมือครั้งแรกใช้เวลานานจนคนอาจเลิกใช้ไปก่อน

**ไอเดียตั้งต้น:** ทำโปรแกรมอ่านหน้าจอ *เฉพาะหน้าต่างเกม* (ไม่อ่านทั้งจอ เพื่อความเป็นส่วนตัว) ให้ user กด monster ทีละตัว เก็บผลเป็น JSON แล้วนำมา import ที่เว็บ

### ทางเลือก

| วิธี | แรงที่ต้องลง | ผลที่ได้ | ข้อควรระวัง |
|---|---|---|---|
| **A. Paste จาก Spreadsheet** | ต่ำ | สูงสำหรับคนที่จดไว้แล้ว | ต้องออกแบบให้ยืดหยุ่นกับรูปแบบตารางที่หลากหลาย |
| **B. Screenshot + OCR ฝั่ง client** | กลาง | สูง | ความแม่นของ OCR กับฟอนต์ในเกม ต้องให้ user ยืนยันก่อนบันทึกเสมอ |
| **C. Desktop helper** | สูง | สูงสุด | ต้องแจกไฟล์ติดตั้ง, ขอ permission บันทึกหน้าจอ, ดูแลข้ามแพลตฟอร์ม |

### A. Paste จาก Spreadsheet

คนที่เล่นจริงจังมักจดไว้ใน Excel หรือ Google Sheets อยู่แล้ว ให้ copy ทั้งตารางมา paste ลงช่องเดียวแล้ว parse เป็น TSV

- ทำเสร็จได้ในไม่กี่ชั่วโมง
- ไม่ต้องติดตั้งอะไรเพิ่ม
- ช่วยเฉพาะคนที่มีข้อมูลเดิมอยู่แล้ว แต่คนกลุ่มนั้นคือคนที่จะใช้แอปนี้เป็นกลุ่มแรก

### B. Screenshot + OCR ฝั่ง client

ให้ user แคปหน้าจอ MR แล้วลากไฟล์มาวางบนเว็บ ใช้ `tesseract.js` อ่านตัวเลขในเบราว์เซอร์ แล้วแสดงผลให้ยืนยัน/แก้ไขก่อนบันทึก

- ไม่ต้องติดตั้งโปรแกรมเพิ่ม
- ใช้บนมือถือได้ด้วย (แคปจากมือถือแล้ว upload ได้เลย)
- **privacy ดีกว่าไอเดียเดิม** เพราะรูปไม่ถูกส่งขึ้น server เลย ประมวลผลในเครื่องล้วน ๆ และ user เป็นคนเลือกเองว่าจะให้รูปไหน
- ความเสี่ยงหลักคือความแม่นของ OCR — แก้ด้วยการบังคับให้ยืนยันก่อนบันทึกเสมอ ไม่บันทึกอัตโนมัติ

### C. Desktop helper (ไอเดียเดิม)

Tauri หรือ Electron เลือก capture เฉพาะ window ของเกม + crop เป็น region → OCR → export JSON

- แม่นและสะดวกที่สุดถ้าทำเสร็จ เพราะควบคุมได้ว่าจะอ่านตรงไหนของหน้าจอ
- Tauri กินทรัพยากรน้อยกว่า Electron มาก น่าจะเหมาะกว่า
- ต้องแจกไฟล์ติดตั้ง มี friction สูง
- macOS ต้องขอ Screen Recording permission ซึ่งจัดการยุ่งพอควร
- ต้อง build และทดสอบหลายแพลตฟอร์ม

### ข้อเสนอ

ทำ **A แล้วตามด้วย B** ก่อน เพราะได้ผลลัพธ์ราว 80% ด้วยแรงประมาณ 20% ทั้งคู่อยู่ในเว็บ ไม่ต้องแจกไฟล์ติดตั้ง

เก็บ **C** ไว้ตัดสินใจหลังจากมีคนใช้จริงแล้ว ถ้ายังมีเสียงบ่นเรื่อง setup อยู่ค่อยลงแรงทำ — ตอนนั้นจะรู้ด้วยว่าหน้าจอส่วนไหนที่ควร capture จริง ๆ

**หมายเหตุ:** ไม่ว่าจะเลือกทางไหน format ปลายทางควรเป็น JSON schema เดียวกัน เพื่อให้ import endpoint ที่เว็บมีทางเดียว

## 3. Static data จะเอามาจากไหน

**ข้อสรุป (2026-08-06):** เจ้าของโปรเจกต์กรอกเองจากในเกมแล้วเตรียมเป็นไฟล์ JSON นำเข้า repo เป็น static data ชุดแรก (Phase 1 ไม่ต้องรอครบทุกธาตุ) ทางเลือกอื่นด้านล่างเก็บไว้เผื่ออนาคต

ทางเลือกที่เคยชั่งน้ำหนัก:

- กรอกเองครั้งเดียวจากในเกม — เหนื่อยแต่ชัวร์และถูกต้องแน่นอน
- ดึงจาก community wiki / database ที่มีอยู่ — เร็วกว่า แต่ต้องเช็คว่าตรงกับเวอร์ชัน Classic ไหม และเรื่องลิขสิทธิ์
- crowdsource — ให้ user ช่วยแก้ผ่าน PR

ไม่ว่าทางไหน ต้องมีแผนรับมือตอนเกมออกแพตช์เพิ่ม monster ใหม่ อย่างน้อยควรออกแบบ schema ให้ static data มี `version` ติดไว้ และเตือน user เมื่อมี row ใหม่ที่ยังไม่ได้กรอก

## 4. Online database

**ข้อสรุป (2026-08-09):** ใช้ **PostgreSQL** บน platform ที่เจ้าของโปรเจกต์มีอยู่แล้ว (ตัวเลือกที่สร้างได้: PostgreSQL / Redis / MongoDB / MySQL — ไม่มี Cloudflare D1) เหตุผล: เป็น relational DB ที่ยืดหยุ่นสุดสำหรับทั้ง alert config (Phase 3) และ cloud sync ในอนาคต, ecosystem ดีสุดในสี่ตัวนี้ ส่วน Redis เหมาะเป็น cache ไม่เหมาะเป็น primary store, Mongo/MySQL ไม่มีข้อได้เปรียบ

**ข้อสรุปเพิ่มเติม (2026-08-09 คุยรอบสอง — เคาะ stack ทั้งชุด):**

- **ORM: Drizzle** — เบา, TypeScript-first, ไม่มี codegen step, เหมาะกับ schema เล็ก ๆ ของเรา
- **Hosting: Vercel (free) สำหรับตัวเว็บ + Railway เฉพาะ Postgres** (เดิมวางไว้ให้ cron ของ Market Alert รันบน Railway ด้วย — ยกเลิกไปพร้อม Phase 3 เมื่อ 2026-10-08)
- **Auth: Auth.js (NextAuth) ใน Next.js เอง** — Sign in with Discord / Google, session แบบ JWT, เก็บ user ลง Postgres ผ่าน Drizzle **ไม่แยก BE** เพราะ Next.js route handlers / server actions คือ server layer อยู่แล้ว
- **ไม่ใช้ Supabase** — เหตุผลหลักคือ cost (Postgres บน Railway ที่มีอยู่ ~$1/เดือน) และ Auth.js ปิดช่องว่างเรื่อง OAuth ได้ฟรี
- **ทำ auth เป็นงานแรกของ Phase 1** (เจ้าของโปรเจกต์ยืนยัน) โดยมีเงื่อนไขคงเดิม: account เป็น optional — tracker ต้องใช้ได้เต็มรูปแบบโดยไม่ login ตาม privacy stance
- ข้อควรระวัง production: Vercel functions เป็น serverless แต่ Railway Postgres มี connection limit ต่ำ → รวม DB access ไว้ที่ Drizzle client module เดียว pool เล็ก และใช้ JWT session เพื่อไม่ให้ request ปกติแตะ DB เลย + Railway Postgres ต้องเปิด public connection ให้ Vercel ต่อได้

**✅ ใช้จริงแล้ว (2026-08-10):** stack ทั้งชุดติดตั้งครบและ cloud sync ขึ้นระบบแล้ว — ตาราง `progress_snapshot` (snapshot ทั้งก้อนต่อ user, JSON schema เดียวกับ Export/Import ตามที่วางไว้) + `PUT`/`GET /api/progress` (session-guarded); อัปโหลดจากเมนูบัญชี, อัปโหลด/restore จากหน้า Backup

**Postgres เปล่า vs Supabase (ชั่งน้ำหนักแล้ว 2026-08-09):** Supabase ข้างในคือ Postgres เหมือนกัน — ของที่ซื้อเพิ่มคือ Auth สำเร็จรูป + API อัตโนมัติ (PostgREST + Row Level Security) ที่ทำให้ client คุยกับ DB ตรง ๆ ได้โดยไม่ต้องเขียน backend เอง ซึ่งจะคุ้ม **เฉพาะเมื่อทำ account + cloud sync จริง** ส่วนงาน Phase 3 (alert config ไม่กี่แถว ไม่มี auth) Postgres บน platform เดิมพอและไม่เพิ่มเจ้าที่สอง ข้อจำกัด Supabase free tier: โปรเจกต์โดน pause เมื่อไม่มีการใช้งาน ~1 สัปดาห์ → **สรุป: เริ่ม Postgres เดิม ถ้า cloud sync มาแน่ค่อยเปิด Supabase — ย้ายไม่เจ็บเพราะเป็น Postgres ทั้งคู่ (dump/restore ตรง ๆ)**

การวิเคราะห์เดิม (ก่อนรู้ว่ามี platform อยู่แล้ว) เก็บไว้ด้านล่างเผื่อกลับมาทบทวน:

**ปัญหา:** อยากเลือกไว้ล่วงหน้าว่าถ้าต้องมี DB ฝั่ง server จะใช้อะไร จะได้ออกแบบส่วนอื่นให้สอดคล้องกัน

**สิ่งที่ต้องใช้ DB online จริง ๆ มีแค่สองเรื่อง** (ทั้งคู่ยังไม่ถึงเวลา):

1. **Phase 3 — Market alert:** เก็บ config การเตือนของ user (Discord webhook URL, เวลารอบตลาด, lead time) ให้ Worker cron อ่านไปยิงแจ้งเตือน — ข้อมูลจิ๋วมาก
2. **อนาคต (ยังเป็นคำถามใน OPEN-QUESTIONS):** account + cloud sync ของ MR progress — ต้องมี auth ประกอบ

### ทางเลือก

| ทางเลือก | จุดแข็ง | ข้อควรระวัง |
|---|---|---|
| **Cloudflare D1** (SQLite) | อยู่ platform เดียวกับ Worker ที่ตัดสินใจไว้แล้ว, SQL เต็มรูป, free tier พอใช้ยาว | ไม่มี auth ในตัว (ต้องทำเองหรือใช้ OAuth ภายนอกตอนทำ sync) |
| **Cloudflare KV** | ง่ายสุดถ้าเก็บแค่ alert config (key = user id) | ไม่เหมาะกับข้อมูล relational / query ซับซ้อน |
| **Supabase** (Postgres) | Auth + DB + realtime ครบในตัว เหมาะถ้า cloud sync มาแน่ | เพิ่ม platform ที่สองที่ต้องดูแล, เกินความต้องการของ Phase 3 มาก |
| **Turso / Neon** | SQLite/Postgres edge ที่ดี | ไม่มีข้อได้เปรียบเหนือ D1 ในเมื่อ compute อยู่บน Cloudflare อยู่แล้ว |

### ข้อเสนอ

ใช้ **Cloudflare D1** เป็นคำตอบหลัก (Phase 3 จะเริ่มด้วย KV ก่อนก็ได้ถ้าเก็บแค่ config) — เหตุผลหลักคือ **ไปทาง Cloudflare ทั้ง stack ตามที่ตัดสินใจเรื่อง Worker ไว้แล้ว** ถ้าวันหน้า cloud sync กลายเป็นของจริงและอยากได้ auth สำเร็จรูป ค่อยชั่งน้ำหนัก Supabase อีกทีตอนนั้น

**สิ่งที่ "ทำไว้ก่อน" ได้ตอนนี้โดยไม่เสียเปล่า:**

- สมัคร/ผูกบัญชี Cloudflare ของโปรเจกต์ไว้ (ฟรี) — ยังไม่ต้อง provision D1 จนกว่าจะถึง Phase 3
- ออกแบบ **Export/Import JSON schema (Phase 2) ให้เป็น schema เดียวกับที่ sync จะใช้** — นี่คือการเตรียมตัวที่คุ้มที่สุด เพราะ sync คือการส่ง JSON ก้อนเดียวกันนี้ขึ้น server แค่นั้น
- คงหลัก privacy เดิม: ข้อมูล user ขึ้น server เฉพาะเมื่อ user เปิดใช้ฟีเจอร์นั้นเอง (opt-in) ค่า default คือ local ล้วน

### Filter แมพควรกรองระดับไหน

ตามที่ระบุไว้คือระดับ **row** (มี monster จากแมพที่ไม่เลือก = ซ่อนทั้งแถว) แต่กรองระดับ **monster** (ซ่อนเฉพาะตัว แล้วคำนวณ row level จากตัวที่เหลือ) ก็สมเหตุสมผล

ข้อเสนอ: ทำระดับ row ก่อนตามที่ออกแบบไว้ แล้วลองใช้จริงสักพัก ถ้าพบว่ากรองแล้วเหลือแถวน้อยเกินไปจนใช้ไม่ได้ ค่อยเพิ่มเป็น option

**✅ ใช้จริงแล้ว (2026-08-10)** — ทำเป็น "แมพที่ไม่ไป" (avoid-list) ตัดสินที่ระดับทริปของแถว: แมพที่เลี่ยงจะถูกข้ามตอนคำนวณทริปคุ้มสุด และแถวที่อัปได้เฉพาะบนแมพที่เลี่ยงจะถูกซ่อน/ลดอันดับตาม toggle เดียวกับ filter อื่น (`MapFilter.tsx` — modal จัดกลุ่มแมพตามช่วงเลเวล 20)

## 6. ประวัติ DEF Planner — เก็บที่ไหน และ sync อย่างไร

**✅ ตัดสินใจและใช้จริงแล้ว (2026-10-08)** — ผู้ใช้ขอให้ประวัติอยู่ในเครื่องเป็นค่าเริ่มต้น และเลือกเองได้ว่าจะ sync เข้า DB หรือไม่

- **Local-first:** snapshot อยู่ใน Dexie ตาราง `defenseHistory` (v4) เก็บเฉพาะ input ไม่เก็บผล — กราฟคำนวณใหม่ทุกจุดกับคู่ต่อสู้ชุดเดียวกัน จึงเทียบกันได้และอัปเดตสูตรย้อนหลังได้
- **Opt-in ต่อเครื่องและต่อบัญชี:** setting `defense.cloudSync` เก็บ user id ของบัญชีที่เปิดไว้ (ไม่ sync ไปกับ payload ใด) — คนอื่นที่ login บนเบราว์เซอร์เดียวกันจะไม่ได้ upload ประวัตินี้เข้าบัญชีตัวเองโดยไม่ได้ตั้งใจ
- **แยกจาก progress sync:** ตาราง Postgres `defense_history` (หนึ่งแถวต่อ user) + `/api/defense-history` (GET/PUT/DELETE) ไม่ปนกับ `progress_snapshot`
- **Merge ราย record แทน last-write-wins ทั้งก้อน:** เหตุผลคือการเปิด sync บนเครื่องที่สองต้องไม่ลบประวัติจากเครื่องแรก — PUT ให้ server merge (ล็อกแถวด้วย `SELECT … FOR UPDATE`) แล้วตอบรายการที่ merge แล้วกลับมา; การลบเป็น tombstone เพื่อให้ชนะการ merge ด้วย (`mergeHistory` ใน `src/features/defense/history.ts`, มี test)
- **ปิด sync:** เลือกได้ว่าจะเก็บหรือลบสำเนาใน cloud; ข้อมูลในเครื่องไม่หาย
- ข้อจำกัด: สูงสุด 500 snapshot ต่อคน (ปุ่มบันทึกปิดเมื่อเต็ม), tombstone ยังไม่ถูก prune — ถ้าเริ่มสะสมเยอะค่อยเพิ่มการ prune ตามอายุ
